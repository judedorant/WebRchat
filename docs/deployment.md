# Deployment template

Phases 1–3 provide deployment scaffolding and account authentication/authorization. This is not yet suitable for public chat usage: messaging, upload security, moderation and later security validation remain future work. Do not expose an unfinished application as a production messaging service.

1. Use Docker Engine with Compose v2, or build these images in CI and deploy by immutable digest. Review base-image updates and scan images/dependencies.
2. Copy `.env.example` to `.env`, generate distinct strong MySQL credentials and configure matching `backend/.env` values. Never commit these files. Obtain secrets through your deployment secret manager. Generate and preserve one `APP_KEY` securely. Set `APP_ENV=production`, `APP_DEBUG=false`, `APP_URL=https://chat.example.com`, `SESSION_SECURE_COOKIE=true`, the exact `SANCTUM_STATEFUL_DOMAINS`, and `REVERB_ALLOWED_ORIGINS=chat.example.com`. Keep server-side publishing on the private Compose network with `REVERB_HOST=reverb`, `REVERB_PORT=8080`, `REVERB_SCHEME=http`. Phase 5 Echo clients must use the public WSS host/port and gateway path `/ws`, separately from these server-side settings. Configure a real verified SMTP provider; the development Mailpit inbox is not deployed by production Compose. See authentication.md for trusted proxies, signed links and mail settings.
3. Build with `docker compose -f compose.production.yaml build`. In managed Cloud, supply the optional `proxy_ca` build secret if the proxy intercepts HTTPS; see README. No TLS verification should be disabled.
4. Start persistence with `docker compose -f compose.production.yaml up -d mysql redis`. Install production vendor files in the image; no host `vendor` mount is used.
5. Run `docker compose -f compose.production.yaml run --rm backend php artisan migrate --force` and then `docker compose -f compose.production.yaml run --rm backend php artisan db:seed --class=RoleSeeder --force`. Back up before migrations; do not run `migrate:fresh` against persistent data.
6. Start with `docker compose -f compose.production.yaml up -d --wait`. Nginx exposes only a loopback port by default. Put a TLS ingress in front of it; it must forward `/ws/*` WebSocket upgrades (the frontend Nginx strips `/ws` before forwarding to Reverb). Configure trusted proxies with exact ingress addresses before trusting forwarded HTTPS headers; do not trust all proxies. If using HTTPS only at the outer ingress, adjust the gateway's forwarded-proto configuration for that trusted ingress rather than silently trusting arbitrary client headers.
7. Request `/api/v1/health`, verify the SPA deep-link `/roadmap`, inspect service health, and run smoke tests against the deployment. The readiness endpoint returns only status, not exception text or credentials. Restrict infrastructure visibility at the edge if necessary.
8. Configure restart/monitoring alerts for workers and Reverb. Restart workers (`queue:restart`) and Reverb (`reverb:restart`) on code/config deployments. Deploy an explicit scheduler service when scheduled jobs are introduced. No scheduler is currently required.

MySQL and Redis have no published host ports. Use encrypted disks and backups, least-privilege network access, and a MySQL account scoped to this database. Redis is intentionally unauthenticated on the private Compose network; a shared infrastructure deployment must add ACLs/TLS and dedicated credentials. Do not expose port 6379. Back up private attachments and the database consistently; test restore, key retention and disaster recovery. Production file storage remains private; add an authorized controller and scanning pipeline in Phase 7. Never run `storage:link` for private attachments.

Before public launch, finish all phases and perform authorization, CORS/CSRF, session fixation, password reset, upload scanning, rate-limit, moderation privacy and load/reconnect reviews. Pin release image digests, run tests on MySQL, establish logs without content/secrets, and configure retention. Cache configuration/routes only after required secrets are injected; cached config and running processes must be refreshed on changes. The production template itself is validated separately from the development stack; do not infer production deployment from a successful dev build.
